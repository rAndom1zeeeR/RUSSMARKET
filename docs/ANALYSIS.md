# Анализ проекта: проблемы и предложения

Состояние на коммит `0774e34` (SQLite локально, Postgres на проде). Разобраны сервер, клиент, инфраструктура и документация.

У каждой находки указано, как она установлена:

- **проверено** — воспроизведено замером или тестом;
- **по коду** — следует из чтения кода, отдельно не воспроизводилось.

Приоритеты: **P1** — баг или риск, который стоит закрыть; **P2** — надёжность, UX, доступность; **P3** — оптимизация и гигиена.

## P1 — баги и риски

### 1. Удаление 500+ ячеек падает на SQLite — **проверено**

`saveShifts` удаляет смены одним `deleteMany` с `OR` по парам `(employeeId, date)`: два параметра на ячейку плюс `scheduleId`. У SQLite лимит параметров запроса (999), поэтому уже на 500 ячейках запрос не выполняется:

```
DELETE 500:  error = The query parameter limit supported by your database is exceeded.
DELETE 5000: error = The query parameter limit supported by your database is exceeded.
```

Схема `saveShiftsSchema` при этом пропускает до 5000 удалений, и API отвечает 500. В интерфейсе это достижимо: «Очистить» по большому выделению в месяце или «Очистить день» при большом штате.

**Предложение:** удалять пачками (по 400 ячеек) или группировать по дате: `{ date, employeeId: { in: [...] } }` — один параметр на сотрудника. Добавить тест на 1000+ удалений.

### 2. Большое сохранение медленное и рискует таймаутом — **проверено** (SQLite) / **по коду** (Postgres)

Upsert идёт отдельным запросом на каждую смену внутри интерактивной транзакции. Замер на локальной SQLite:

```
UPSERT 1000: 633 ms
UPSERT 5000: 2710 ms
```

У интерактивной транзакции Prisma таймаут по умолчанию 5 с. На Postgres каждый запрос — сетевой round-trip, так что пачка в несколько тысяч смен почти наверняка его превысит и откатится целиком. На живом Postgres не проверялось.

**Предложение:** `deleteMany` по ключам затронутых ячеек + один `createMany` вместо тысяч upsert-ов (2–3 запроса на любое сохранение). Либо задать `timeout` у транзакции и снизить лимит схемы до реального максимума (сотрудники × дни месяца).

### 3. Быстрое назначение расходится с решением §10.1 — **по коду**

В `docs/PLAN.md` §10.1 записано: смена по клику на дату ставится **всем** сотрудникам, поиск список не сужает. В коде `SchedulePage` передаёт в `QuickAssignMenu` уже отфильтрованных сотрудников. E2E-тест `views.spec.ts` («применяется только к найденным сотрудникам») и главная описывают именно текущее поведение.

**Предложение:** передавать в меню полный список сотрудников, поправить E2E-тест, unit-тест и тексты на главной.

### 4. Изменяющие API открыты без авторизации — **по коду**

`PUT /api/schedules/:id/shifts` и `POST /api/schedules/:id/publish` доступны любому, кто знает адрес задеплоенного сервера: можно перезаписать или опубликовать график. Авторизации нет по ТЗ, но сервер уже публичный.

**Предложение:** минимум — Basic Auth на уровне прокси Dokploy или проверка токена из переменной окружения в `proxy.ts` (в Next 16 это бывший `middleware.ts`) для не-GET запросов к `/api`.

### 5. Стартовая дата периода «застывает» на сервере — **по коду**

Хранилище Zustand задаёт `anchor: todayISO()` при загрузке модуля. `SchedulePage` — клиентский компонент, но рендерится и на сервере (SSR). На сервере модуль загружается один раз на процесс, в часовом поясе сервера. Значит, заголовок периода в серверном HTML — это дата **запуска сервера**. В браузере модуль загружается заново с актуальной датой. Через сутки работы прод-сервера или при разных часовых поясах (сервер в UTC, пользователь в UTC+3 после полуночи) серверный и клиентский заголовки не совпадут. React сообщит об ошибке гидратации и перерисует дерево на клиенте. Не воспроизводилось: нужен долго работающий сервер или разные часовые пояса.

**Предложение:** не считать дату при загрузке модуля. Варианты: вычислять `anchor` на клиенте после монтирования (до этого показывать скелетон) или передавать «сегодня» со страницы в часовом поясе пользователя.

## P2 — надёжность, UX, доступность

### 6. Правки теряются без предупреждения — **по коду**

Черновик живёт только в памяти. Перезагрузка, закрытие вкладки или переход на главную сбрасывают несохранённые правки молча.

**Предложение:** `beforeunload` при непустом черновике и подтверждение при переходе по ссылкам меню.

### 7. Черновик и выделение не привязаны к графику — **по коду**

Ключ ячейки `employeeId|date` не содержит `scheduleId`, а хранилище одно на всё приложение. Если открыть другой график, правки и выделение первого применятся к нему. Сейчас график один, поэтому проблема скрыта.

**Предложение:** сбрасывать черновик и выделение при смене `scheduleId` или хранить черновик по `scheduleId`.

### 8. Выделение действует на скрытые поиском ячейки — **по коду**

Поиск намеренно не снимает выделение (так зафиксировано в тестах). Но «Применить шаблон» и «Очистить» тогда затрагивают ячейки сотрудников, которых не видно на экране.

**Предложение:** при поиске пересекать выделение с видимыми строками или показывать в панели выделения «N скрыто поиском».

### 9. `Esc` снимает выделение, даже когда закрывает попап — **по коду**

Сетка вешает обработчик `keydown` на `window`. Нажатие `Esc`, чтобы закрыть попап «Изменить время» или меню даты, заодно снимает выделение.

**Предложение:** не реагировать, если событие уже обработано (`defaultPrevented`) или фокус внутри диалога.

### 10. Нет защиты от одновременной правки — **по коду**

Два редактора, которые меняют одни и те же ячейки, молча перезаписывают друг друга. Последняя запись побеждает. Diff ограничивает ущерб только затронутыми ячейками.

**Предложение:** передавать `updatedAt` графика в `PUT` и отвечать 409, если он изменился. Клиент предложит перезагрузить данные.

### 11. Длина периода в `GET …/shifts` не ограничена — **по коду**

Схема проверяет только формат дат. Запрос `from=1900-01-01&to=2999-12-31` выгрузит все смены, а `from > to` вернёт пустой ответ без ошибки.

**Предложение:** в `shiftsQuerySchema` требовать `from ≤ to` и период не длиннее, например, 62 дней.

### 12. Сидер стирает данные без защиты — **по коду**

`prisma/seed.ts` удаляет всех сотрудников, шаблоны, графики и смены. Об этом предупреждают README и AGENTS.md, но кода, который бы помешал, нет: одно случайное `pnpm db:setup` с боевым `DATABASE_URL` уничтожит данные.

**Предложение:** отказываться работать, если в базе уже есть графики, без явного `SEED_FORCE=1`.

### 13. Смена периода: запросы не отменяются, нет индикатора — **по коду**

`api()` не передаёт `signal` из TanStack Query в `fetch`, поэтому быстрые переключения недель не отменяют старые запросы. С `keepPreviousData` при переходе на новую неделю `isLoading` остаётся `false`. Новые даты при этом не совпадают со старыми данными, и сетка ненадолго выглядит пустой, будто смен нет.

**Предложение:** пробрасывать `signal` и показывать индикатор по `isPlaceholderData`.

### 14. Сетка не управляется с клавиатуры — **по коду**

Ячейки — `div role="gridcell"` без `tabIndex`: на них нельзя попасть с клавиатуры, нет навигации стрелками и выделения по `Enter`/`Space`. Перетаскивание работает только мышью и касанием (`KeyboardSensor` dnd-kit не подключён). Пункт «Полировка: a11y, клавиатура» из плана выполнен частично: роли проставлены, фокуса и клавиатуры нет.

**Предложение:** roving tabindex по сетке, стрелки для перемещения, `Space`/`Enter` для выделения, `Shift+стрелки` для диапазона.

### 15. Контраст подписей ниже WCAG AA — **проверено** (расчёт)

Длительность смены (12 px) на фоне чипа:

| Тон     | Текст     | Фон       | Контраст | Нужно для AA |
| ------- | --------- | --------- | -------- | ------------ |
| «Вечер» | `#00c7be` | `#e0f8f7` | ≈ 1,9:1  | 4,5:1        |
| «День»  | `#915aff` | `#e9deff` | ≈ 3,2:1  | 4,5:1        |

Цвета взяты из макета. Это вопрос к дизайну: например, затемнить акцентные цвета для текста, оставив фон.

## P3 — оптимизация и гигиена

### 16. Лишние перерисовки сетки — **по коду**

В `schedule-grid.tsx` стоит `"use no memo"` (это нужно для TanStack Virtual), поэтому обработчики ячеек создаются заново на каждый рендер. Каждое `pointerenter` при протяжке выделения обновляет хранилище и перерисовывает все видимые ячейки. В месяце это до ~370 ячеек, у каждой хуки dnd-kit. Профилировщиком не замерялось.

**Предложение:** стабильные обработчики (через ref) и `memo(GridCell)`. Сначала замерить React Profiler на «Месяце».

### 17. Прод-образ тащит SQLite — **по коду**

Прод работает на Postgres. Но `better-sqlite3` собирается нативно (`python3 make g++` в двух стадиях Dockerfile), а адаптер SQLite попадает в standalone-трассировку через динамический `import()`.

**Предложение:** исключить SQLite-пакеты из трассировки (`outputFileTracingExcludes`) и проверить, можно ли не ставить тулчейн. Сборка образа станет быстрее, а сам образ меньше.

### 18. Healthcheck и corepack в Dockerfile — **по коду**

- `HEALTHCHECK` жёстко бьёт в порт 3000 и в `/`. Главная статична, поэтому healthcheck зелёный даже при недоступной базе. В compose проверка своя и учитывает `PORT`, но тоже смотрит на `/`.
- `COREPACK_INTEGRITY_KEYS=0` отключает проверку подписи скачиваемого pnpm.

**Предложение:** `GET /api/health` с запросом к базе, healthcheck на `${PORT}` и этот адрес; убрать `COREPACK_INTEGRITY_KEYS=0`.

### 19. CI не проверяет Postgres и Docker — **по коду**

Postgres-путь (миграция, сидер, запросы) на живой базе никогда не запускался, а Dockerfile не собирается до деплоя.

**Предложение:** job с `services: postgres` в GitHub Actions: `migrate deploy`, сидер, серверные тесты против Postgres. Плюс job `docker build`.

### 20. Мелочи — **по коду**

- `package.json`: `"name": "nextjs-base"` — имя стартового шаблона.
- `schedule-grid.tsx`: в `dragRef` поле `base` нигде не читается.
- AGENTS.md запрещал добавлять Playwright, хотя он уже в `package.json` (исправлено в этом обновлении).
- `docs/PLAN.md` описывал SQLite как единственную базу и тесты как «вне объёма» (исправлено в этом обновлении).

## Что в порядке

- Слои FSD, границы проверяет линтер. БД трогает только `src/server`, схемы запросов общие для клиента и сервера (zod).
- Модель черновика: сохраняется diff одной транзакцией, атомарность подтверждена тестом.
- Тесты: 492 теста Vitest (покрытие ~99% строк, 95% веток) и 42 E2E на настоящем браузере, включая перетаскивание мышью и мобильную версию.
- Выбор базы по `DATABASE_URL`, оба клиента Prisma генерируются, схемы сверяются тестом.
- Ошибки API не раскрывают внутренние детали, а пароль из `DATABASE_URL` не попадает в сообщения.
