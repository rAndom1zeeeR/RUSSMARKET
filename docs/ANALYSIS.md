## P1 — баги и риски

### 1. Удаление 500+ ячеек падает на SQLite — **проверено**, **исправлено**

`saveShifts` удаляет смены одним `deleteMany` с `OR` по парам `(employeeId, date)`: два параметра на ячейку плюс `scheduleId`. У SQLite лимит параметров запроса (999), поэтому уже на 500 ячейках запрос не выполняется:

```
DELETE 500:  error = The query parameter limit supported by your database is exceeded.
DELETE 5000: error = The query parameter limit supported by your database is exceeded.
```

Схема `saveShiftsSchema` при этом пропускает до 5000 удалений, и API отвечает 500. В интерфейсе это достижимо: «Очистить» по большому выделению в месяце или «Очистить день» при большом штате.

**Предложение:** удалять пачками (по 400 ячеек) или группировать по дате: `{ date, employeeId: { in: [...] } }` — один параметр на сотрудника. Добавить тест на 1000+ удалений.

**Исправлено** вместе с №2 — см. ниже.

### 2. Большое сохранение медленное и рискует таймаутом — **проверено** (SQLite) / **по коду** (Postgres), **исправлено**

Upsert идёт отдельным запросом на каждую смену внутри интерактивной транзакции. Замер на локальной SQLite:

```
UPSERT 1000: 633 ms
UPSERT 5000: 2710 ms
```

У интерактивной транзакции Prisma таймаут по умолчанию 5 с. На Postgres каждый запрос — сетевой round-trip, так что пачка в несколько тысяч смен почти наверняка его превысит и откатится целиком. На живом Postgres не проверялось.

**Предложение:** `deleteMany` по ключам затронутых ячеек + один `createMany` вместо тысяч upsert-ов (2–3 запроса на любое сохранение). Либо задать `timeout` у транзакции и снизить лимит схемы до реального максимума (сотрудники × дни месяца).

**Исправлено.** `saveShifts` удаляет все затронутые ячейки пачками по 400 (≤ 801 параметр) и вставляет новые значения через `createMany` пачками по 120 (≤ 840 параметров), всё в одной пакетной транзакции `$transaction([...])` — у неё нет таймаута интерактивной транзакции. Замер на SQLite: удаление 1000 ячеек — 78 мс, 5000 — 679 мс; сохранение 5000 смен — 789 мс вместо 2710 мс; запросов на 5000 смен — 56 вместо ~5000. Тесты: 5000 удалений и вставок, границы пачек, смешанный diff, дубли ячеек, откат при ошибке в последней пачке, число пачек. На живом Postgres не прогонялось: пачки укладываются в его лимит параметров (65 535) с большим запасом.

### 3. Быстрое назначение расходится с решением §10.1 — **по коду**, **исправлено**

В `docs/PLAN.md` §10.1 записано: смена по клику на дату ставится **всем** сотрудникам, поиск список не сужает. В коде `SchedulePage` передаёт в `QuickAssignMenu` уже отфильтрованных сотрудников. E2E-тест `views.spec.ts` («применяется только к найденным сотрудникам») и главная описывают именно текущее поведение.

**Предложение:** передавать в меню полный список сотрудников, поправить E2E-тест, unit-тест и тексты на главной.

**Исправлено.** `useScheduleData` отдаёт и отфильтрованных сотрудников (для сетки), и всех (`allEmployees`); меню даты получает всех. Поиск больше не сужает быстрое назначение: заголовок меню показывает полное число сотрудников. Тесты: страница (`schedule-page.test.tsx`) и E2E (`views.spec.ts`) — поиск сузил список до одного, смена встала всем восьми.

### 4. Изменяющие API открыты без авторизации — **по коду**

`PUT /api/schedules/:id/shifts` и `POST /api/schedules/:id/publish` доступны любому, кто знает адрес задеплоенного сервера: можно перезаписать или опубликовать график. Авторизации нет по ТЗ, но сервер уже публичный.

**Предложение:** минимум — Basic Auth на уровне прокси Dokploy или проверка токена из переменной окружения в `proxy.ts` (в Next 16 это бывший `middleware.ts`) для не-GET запросов к `/api`.

### 5. Стартовая дата периода «застывает» на сервере — **по коду**, **исправлено**

Хранилище Zustand задаёт `anchor: todayISO()` при загрузке модуля. `SchedulePage` — клиентский компонент, но рендерится и на сервере (SSR). На сервере модуль загружается один раз на процесс, в часовом поясе сервера. Значит, заголовок периода в серверном HTML — это дата **запуска сервера**. В браузере модуль загружается заново с актуальной датой. Через сутки работы прод-сервера или при разных часовых поясах (сервер в UTC, пользователь в UTC+3 после полуночи) серверный и клиентский заголовки не совпадут. React сообщит об ошибке гидратации и перерисует дерево на клиенте. Не воспроизводилось: нужен долго работающий сервер или разные часовые пояса.

**Предложение:** не считать дату при загрузке модуля. Варианты: вычислять `anchor` на клиенте после монтирования (до этого показывать скелетон) или передавать «сегодня» со страницы в часовом поясе пользователя.

**Исправлено.** В хранилище `anchor` теперь `null` до монтирования, «сегодня» выставляет `ensureAnchor()` в `useLayoutEffect` страницы графика — только в браузере, в часовом поясе пользователя и до отрисовки (без мигания). Пока даты нет, страница рендерит заготовку «Загрузка графика…», поэтому серверный HTML от даты не зависит. Уже выбранный период при повторном открытии страницы не сбрасывается. Тесты: unit (хранилище), страница (`renderToString` без даты, клиентская инициализация) и E2E `timezone.spec.ts` — браузер в UTC+14 и UTC−11: в серверном HTML нет даты, ошибок гидратации нет, показана неделя по часам браузера.

## P2 — надёжность, UX, доступность

### 6. Правки теряются без предупреждения — **по коду**, **исправлено**

**Исправлено.** Пока в черновике есть правки, `useUnsavedChangesGuard` включает `beforeunload` (закрытие вкладки, перезагрузка) и перехватывает клики по внутренним ссылкам (меню, логотип) с подтверждением. Внешние ссылки, ссылки на ту же страницу и клики с модификаторами не спрашивают. Кнопку «назад» браузера (`popstate`) хук не перехватывает: в App Router для этого нет надёжного API. Тесты: хук (6 сценариев), E2E на это не написан.

### 7. Черновик и выделение не привязаны к графику — **по коду**, **исправлено**

**Исправлено.** В хранилище появились `scheduleId` и `bindSchedule()`: страница графика вызывает его при монтировании, при смене графика черновик и выделение сбрасываются. Повторная привязка к тому же графику ничего не трогает. Тесты: хранилище (2).

### 8. Выделение действует на скрытые поиском ячейки — **по коду**, **исправлено**

**Исправлено.** Страница пересекает выделение с видимыми строками: когда поиск скрывает сотрудников, их ячейки выходят из выделения (якорь тоже сбрасывается, если он скрыт). «Применить шаблон» и «Очистить» действуют только на то, что видно. Возврат фильтра выделение не восстанавливает. Быстрое назначение по дате по-прежнему применяется ко всем сотрудникам (решение §10.1, №3). Тест страницы добавлен.

### 9. `Esc` снимает выделение, даже когда закрывает попап — **по коду**, **исправлено**

**Исправлено.** Глобальный `keydown` сетки игнорирует событие, которое уже обработано (`event.defaultPrevented`): попапы и диалоги Radix вызывают `preventDefault` на `Esc`, поэтому первое нажатие закрывает попап, а выделение остаётся. Тест сетки добавлен.

### 10. Нет защиты от одновременной правки — **по коду**, **исправлено**

**Исправлено.** `PUT …/shifts` принимает `expectedUpdatedAt` (версия графика, которую видел клиент). Сервер обновляет график условно (`where: { id, updatedAt }`) внутри той же пакетной транзакции: если версия устарела, обновление не находит строку (`P2025`), транзакция откатывается целиком, и API отвечает **409** «График изменён другим пользователем». Клиент показывает ошибку и перечитывает график и смены; черновик остаётся, следующее сохранение пройдёт поверх свежей версии. Без поля поведение прежнее (обратная совместимость). Тесты: репозиторий, маршрут (409, смены не записаны), схема, клиент.

Ограничение: это защита от потери чужих правок, а не слияние. Конфликтующие ячейки пользователь решает сам.

### 11. Длина периода в `GET …/shifts` не ограничена — **по коду**, **исправлено**

**Исправлено.** `shiftsQuerySchema` проверяет, что даты существуют, `from ≤ to` и период не длиннее `MAX_PERIOD_DAYS = 62` (покрывает месяц с запасом). Нарушение даёт 400 «Некорректные данные». Тесты: схема (границы 62/63 дня, «задом наперёд», «за всё время», несуществующие даты) и маршрут.

### 12. Сидер стирает данные без защиты — **по коду**, **исправлено**

**Исправлено.** `prisma/seed.ts` отказывается работать (код выхода 1, подсказка в stderr), если в базе уже есть графики. Пересоздать данные можно явно: `pnpm db:reseed` (`--force`) или `SEED_FORCE=1`. На пустой базе сидер работает как раньше, поэтому `pnpm db:setup` на новой базе не меняется. E2E-подготовка БД выставляет `SEED_FORCE=1`. Тесты: отказ ничего не меняет, `--force`, `SEED_FORCE`, пустая база.

### 13. Смена периода: запросы не отменяются, нет индикатора — **по коду**, **исправлено**

**Исправлено.** `api()` получает `signal` из TanStack Query во всех запросах: быстрые переключения недель отменяют запросы предыдущих периодов. Пока грузится новый период (`isPlaceholderData`), сетка приглушается, получает `aria-busy` и скрытый статус «Загружаем период…» для скринридеров. Тест страницы с отложенным ответом.

### 14. Сетка не управляется с клавиатуры — **по коду**, **исправлено** (частично)

**Исправлено.** Roving tabindex: в порядке табуляции одна ячейка, остальные достигаются стрелками. Стрелки двигают фокус (с прокруткой виртуализованных строк), `Home`/`End` — к краям строки, `Space`/`Enter` — выделить или снять, `Shift`+стрелки — диапазон. У ячейки есть `aria-label` («Сотрудник, день: смена»), у фокуса — видимое кольцо. Тесты сетки (5).

**Не сделано:** перенос смен с клавиатуры (`KeyboardSensor` dnd-kit). Назначение с клавиатуры возможно: выделить ячейки и применить шаблон из панели выделения.

## P3 — оптимизация и гигиена

### 16. Лишние перерисовки сетки — **по коду**, **исправлено** (не замерялось)

**Исправлено.** `GridCell` обёрнут в `memo`, обработчики сетки стабильны (`useCallback` + ref на актуальные данные, состояние читается через `useScheduleStore.getState()`), поэтому при протяжке выделения перерисовываются только ячейки, у которых изменился `selected`. `"use no memo"` в сетке остаётся из-за TanStack Virtual. Выигрыш React Profiler не замерялся: это изменение по коду, поведение покрыто существующими тестами.

### 17. Прод-образ тащит SQLite — **по коду**, **исправлено** (тулчейн оставлен)

**Исправлено частично.** `outputFileTracingExcludes` убирает из standalone-сборки `better-sqlite3`, адаптеры SQLite и клиент `src/generated/prisma`. Локально собранный `.next/standalone` весит 34 МБ и не содержит SQLite-пакетов; сервер стартует, а `/api/health` без базы отвечает 503. Локальная разработка и тесты берут SQLite из `node_modules` и не затронуты.

**Оставлено осознанно:** `python3 make g++` в стадиях `deps` и `builder` нужны, потому что `pnpm install` собирает `better-sqlite3` для разработки. В итоговый образ (`runner`) они не попадают. Образ целиком в Docker не собирался: демон недоступен.

### 18. Healthcheck и corepack в Dockerfile — **по коду**, **исправлено** (corepack оставлен)

**Исправлено.** Добавлен `GET /api/health`: проверяет базу запросом и отвечает 200 `{ status: "ok" }` или 503 `{ status: "unavailable" }` без деталей. `HEALTHCHECK` в Dockerfile и healthcheck в compose бьют в него и учитывают `PORT`. Тесты маршрута и репозитория.

**Оставлено осознанно:** `COREPACK_INTEGRITY_KEYS=0`. Убирать его не стал: без сборки образа проверить, что `corepack prepare pnpm@12.5.1` пройдёт, нельзя. Флаг действует только в стадиях сборки, в итоговый образ pnpm не попадает.

### 19. CI не проверяет Postgres и Docker — **по коду**, **исправлено** (в CI не запускалось)

**Исправлено.** В `.github/workflows/ci.yml` два новых job:

- `postgres`: сервис `postgres:16`, затем `pnpm db:setup` (миграции и сидер на Postgres), `pnpm build`, запуск сервера и проверка `/api/health`, `/api/employees`, `/api/templates`; в конце проверка, что сидер отказывается трогать непустую базу.
- `docker`: `docker build` образа.

**Честно:** ни Postgres-job, ни Docker-job локально не запускались (нет Postgres и демона Docker), первый прогон будет в CI. Серверные Vitest-тесты по-прежнему идут на SQLite: фикстура `tests/setup/db.ts` собирает базу из SQLite-миграций, Postgres-вариант потребовал бы отдельной схемы на каждый файл.

## Что в порядке

- Слои FSD, границы проверяет линтер. БД трогает только `src/server`, схемы запросов общие для клиента и сервера (zod).
- Модель черновика: сохраняется diff одной транзакцией, атомарность подтверждена тестом.
- Тесты: Vitest (покрытие ~99% строк) и E2E на настоящем браузере, включая перетаскивание мышью и мобильную версию.
- Выбор базы по `DATABASE_URL`, оба клиента Prisma генерируются, схемы сверяются тестом.
