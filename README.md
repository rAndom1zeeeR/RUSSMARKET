# График смен (CRM)

Тестовое задание Fullstack-разработчика: страница рабочего графика сотрудников по макетам Figma.
Просмотр расписания, назначение и редактирование смен, шаблоны, drag-and-drop, «Неделя» / «Месяц»,
сохранение и публикация. Данные хранятся в SQLite локально и в Postgres на проде, интерфейс общается с сервером через Route Handlers.

Next.js 16 · React 19 · TypeScript · Tailwind v4 · TanStack Query / Virtual · Zustand · dnd-kit · Prisma 7 (SQLite / Postgres) · Vitest · Playwright.

## Запуск

```bash
pnpm install
cp .env.example .env     # DATABASE_URL="file:./prisma/data/dev.db" — локальная SQLite
pnpm db:setup            # prisma generate + migrate deploy + seed
pnpm dev                 # http://localhost:$PORT  (PORT из .env, иначе 3000)
```

Файл БД (`prisma/data/dev.db`) в git не хранится. Сидер (`prisma/seed.ts`) создаёт 8 сотрудников,
3 шаблона смен (Утро / День / Вечер) и график с готовыми сменами на текущую неделю;
на непустой базе он отказывается работать и ничего не меняет. Пересоздать данные осознанно: `pnpm db:reseed`
(или `SEED_FORCE=1`); `pnpm db:reset` сбрасывает базу и сидит заново.

## Деплой

Production-сборка — Next.js standalone (`output: "standalone"` в `next.config.ts`). Образ multi-stage на Node 22 (pnpm 12.5.1): зависимости, `prisma generate` + `pnpm build`, раннер с `node server.js`.

[`docker-compose.yml`](docker-compose.yml) написан под Dokploy, не под локальный `docker compose up`:

1. В Dokploy — Compose из репозитория.
2. Domains → сервис `app`, порт контейнера = `PORT` из `.env` (по умолчанию 3000).

База — внешний Postgres: `DATABASE_URL=postgresql://…` задаётся в окружении Dokploy, без него compose не стартует. Тома нет: приложение ничего не хранит на диске. Образ собирается с заглушкой URL, к базе при сборке никто не подключается. Сеть `dokploy-network` внешняя. Healthcheck (Dockerfile и compose) бьёт в `GET /api/health`: 200, если база отвечает, иначе 503. SQLite-драйвер в production-образ не попадает (`outputFileTracingExcludes`).

Таблицы и данные создаются один раз снаружи, с любой машины, где есть репозиторий и доступ к базе:

```bash
DATABASE_URL="postgresql://user:password@host:5432/db" pnpm db:setup   # generate + migrate deploy (Postgres) + seed
```

Сидер **пересоздаёт данные** (удаляет сотрудников, шаблоны, графики и смены), поэтому на базе, где уже есть графики, он отказывается работать (код выхода 1). Принудительно — `pnpm db:reseed` или `SEED_FORCE=1`: на боевой базе с настоящими правками так делать нельзя. Для обновления схемы достаточно `prisma migrate deploy`. Пока таблиц нет, сайт показывает «Графиков пока нет, либо база данных не готова».

## Возможности

- Календарь «Неделя» / «Месяц», навигация по периодам, поиск по ФИО.
- Выделение ячеек: клик, протяжка мышью, Ctrl/⌘-клик, Shift-клик, `Esc` / «Снять». На тач-экранах тап добавляет ячейку. Поиск убирает из выделения скрытых сотрудников.
- Клавиатура: `Tab` входит в сетку, стрелки / `Home` / `End` двигают фокус, `Space` / `Enter` выделяют, `Shift`+стрелки — диапазон.
- Защита правок: браузер спрашивает при закрытии вкладки и переходе по ссылкам, пока есть несохранённое; при одновременной правке сервер отвечает 409, и сохранение не затирает чужие изменения.
- Назначение смен: шаблон кликом, быстрое меню по клику на дату (ставит смену всем сотрудникам, поиск на него не влияет), «Своя смена» с произвольным временем,
  «Изменить» время у выделенных смен, «Очистить».
- Drag-and-drop: шаблон → ячейка (или все выделенные), смена → другая ячейка (перенос, `Alt` — копия).
- Покрытие по датам обновляется мгновенно (красный `0` → голубой с числом).
- Правки копятся в черновике; «Сохранить» отправляет разницу одной транзакцией, «Опубликовать» доступна без несохранённых правок.
- Ночные смены: если конец не позже начала, смена считается через полночь.

## Адаптив

Брейкпоинты заданы в `src/app/globals.css` (`--breakpoint-*`), стандартные брейкпоинты Tailwind отключены.
Подход mobile-first: стили без префикса действуют на всех экранах, `md:` и `lg:` переопределяют их.

| Брейкпоинт | Ширина | Что меняется                                                                                                 |
| ---------- | ------ | ------------------------------------------------------------------------------------------------------------ |
| `sm`       | ≥ 320  | Верхняя панель + выдвижное меню, компактная сетка с горизонтальной прокруткой, панель выделения внизу экрана |
| `md`       | ≥ 640  | Рейка меню с иконками, тулбар в две строки, панель шаблонов под сеткой                                       |
| `lg`       | ≥ 1200 | Макет Figma: меню 280 px, панель шаблонов справа; на 1200–1500 px колонка сотрудников компактнее             |

Размеры сетки, которые нужны в JS (виртуализация), берутся из `useBreakpoint` (`src/shared/lib/use-breakpoint.ts`) —
значения должны совпадать с `globals.css`.

## Тесты

Vitest + Testing Library, три проекта (`vitest.config.mts`):

| Проект   | Среда | Что проверяет                                                                                                     |
| -------- | ----- | ----------------------------------------------------------------------------------------------------------------- |
| `unit`   | node  | даты, время, склонения, модели, zod-схемы, хранилище Zustand, логика сброса при перетаскивании, контент главной   |
| `server` | node  | репозитории и Route Handlers на настоящей временной SQLite (схема из `prisma/migrations`), идемпотентность сидера |
| `dom`    | jsdom | компоненты, хуки, страницы; сценарии «выделить → шаблон → сохранить» целиком через `SchedulePage`                 |

`pnpm test:coverage` печатает отчёт и падает ниже порога (сейчас около 99% строк); CI гоняет его на каждый push и PR.
Серверные тесты создают свою базу во временном каталоге и не трогают `prisma/data/dev.db`.

### E2E

Playwright (`e2e/`) гоняет настоящий браузер против production-сборки: `pnpm e2e`.
Тесты сами собирают приложение, поднимают сервер на порту 3100 и используют отдельную БД `prisma/data/e2e.db`
(рабочая `dev.db` и dev-сервер не затрагиваются); перед каждым тестом данные пересоздаются сидером.
Локально берётся установленный Chrome, в CI ставится Chromium от Playwright.

Что проверяется: открытие графика, назначение шаблона, сохранение и перезагрузка, публикация, своя смена,
быстрое назначение по дате, правка и очистка смен, протяжка выделения, drag-and-drop **настоящей мышью**
(шаблон → ячейка и в выделение, перенос смены, копирование с Alt, порог в 6 px), месяц и навигация, поиск,
главная и меню, мобильная версия 320 px с касаниями, а также часовые пояса браузера (UTC+14 и UTC−11): серверный HTML без даты, гидратация без ошибок. E2E не входит в `pnpm check`, в CI это отдельная задача.

## Архитектура

`src/shared` → `src/entities` → `src/features` → `src/widgets` → `src/app` (границы слоёв проверяет oxlint).

```
src/app/(app)/      страницы под общим каркасом: главная, /schedules, /schedules/[id]
src/app/api/        Route Handlers: employees, templates, schedules/[id], …/shifts, …/publish
src/widgets/        app-shell, schedule-page, project-overview
src/features/       schedule-grid, cell-selection, quick-assign, custom-shift, shift-dnd, schedule-toolbar, schedule-actions
src/entities/       employee, shift-template, shift, schedule (model / api / ui)
src/shared/         ui-компоненты, lib (даты, время, брейкпоинты), http-клиент
src/server/         Prisma-клиент, репозитории, http-хелперы (только на сервере)
prisma/             schema.prisma + migrations (SQLite), postgres/ (схема и миграции Postgres), seed.ts, database-url.ts, data/ (файл SQLite, не в git)
```

Поток данных: UI → черновик правок (Zustand) поверх серверных данных (TanStack Query) → `/api/*` (валидация zod) →
репозитории (Prisma) → SQLite (локально) или Postgres (прод). Отображаемые смены = данные периода + черновик; покрытие и счётчики шаблонов
считаются из них на клиенте.

| Метод и адрес                     | Назначение                                                                               |
| --------------------------------- | ---------------------------------------------------------------------------------------- |
| `GET /api/employees`              | сотрудники                                                                               |
| `GET /api/templates`              | шаблоны смен                                                                             |
| `GET /api/schedules/:id`          | график (название, статус)                                                                |
| `GET /api/schedules/:id/shifts`   | смены за период (`?from=&to=`, не длиннее 62 дней)                                       |
| `PUT /api/schedules/:id/shifts`   | сохранение разницы `{ upserts, deletes, expectedUpdatedAt? }`; 409, если график изменили |
| `GET /api/health`                 | проверка живости и базы (200 / 503)                                                      |
| `POST /api/schedules/:id/publish` | публикация графика                                                                       |

## База данных

Две базы, выбирает **схема `DATABASE_URL`**, а не `NODE_ENV` (его Next выставляет сам, а `NODE_ENV=development` в `.env` ломает `next build`):

| Где                              | `DATABASE_URL`                            | Провайдер | Схема и миграции                                              |
| -------------------------------- | ----------------------------------------- | --------- | ------------------------------------------------------------- |
| Локально: разработка, тесты, E2E | `file:./prisma/data/dev.db`               | SQLite    | `prisma/schema.prisma`, `prisma/migrations`                   |
| Прод                             | `postgresql://user:password@host:5432/db` | Postgres  | `prisma/postgres/schema.prisma`, `prisma/postgres/migrations` |

- Клиент Prisma генерируется для обоих провайдеров (`pnpm db:generate` → `src/generated/prisma` и `src/generated/prisma-postgres`; делает и `postinstall`). В рантайме `src/server/create-client.ts` берёт нужный и грузит только свой адаптер: `better-sqlite3` или `@prisma/adapter-pg`.
- Команды Prisma (`migrate`, `db seed`, `studio`) тоже смотрят на `DATABASE_URL`: `prisma.config.ts` подставляет схему и каталог миграций нужного провайдера.
- Модели в двух схемах должны совпадать: тест `prisma/schemas.test.ts` падает при расхождении. Меняя модель, правьте обе схемы и добавляйте миграцию в оба каталога: для SQLite — `pnpm db:migrate`, для Postgres — то же с `DATABASE_URL=postgresql://…` (нужна доступная база).
- Начальная миграция Postgres сгенерирована командой `prisma migrate diff --from-empty --to-schema prisma/postgres/schema.prisma --script`.

Локально Docker и Postgres не нужны: разработка, тесты и E2E идут на SQLite. Прод — Postgres; в CI задача `postgres` гоняет миграции, сидер и smoke на Postgres 16, задача `docker` собирает образ для Dokploy. Даты и время хранятся строками (`YYYY-MM-DD`, `HH:mm`) — при желании их можно перевести в `Date` / `Time`.

## Известные проблемы

Полный разбор с приоритетами — в [docs/ANALYSIS.md](docs/ANALYSIS.md). Самое важное:

- изменяющие API на проде открыты без авторизации (остальные найденные проблемы исправлены, оговорки — в разборе);
- цвета текста «День», «Вечер», серых подписей и ошибок совпадают с макетом: затемнение ради WCAG AA отменено.
